当前授信 Agent 流程编排

这张图描述系统现在真实执行的流程，而不是目标设计。核心判断是：当前系统由“批量材料分析流水线”和“独立聊天问答接口”两条链路组成，前端负责把它们拼成类似 Agent 的对话体验。

当前本质 它更接近“异步材料处理工作流 + 证据问答服务”，还不是一个拥有统一运行实例、事件流、上下文和输出生命周期的 Agent 编排器。

二、当前状态机能表达什么

只有任务状态和材料状态，没有“某一次 Agent 运行”的状态

任务状态

draft→ materials_processing→ needs_review 或 analysis_complete

单份材料状态

uploaded→ queued→ parsing→ extracting→ ready needs_review / failed
27 份文件为何仍然慢

每份文件至少需要 2 次结构化模型调用，27 份约为 54 次；当前并发上限为 3，意味着至少分 9 批。模型输出校验失败时还会重试。全部材料完成后才执行跨文件冲突审查，而每个冲突又可能增加一次串行模型调用。

三、当前编排的主要断点

这些问题共同造成“像在聊天，但消息、进度和结果没有真正属于同一轮”的体验

01

没有统一 Agent Run

开始分析、普通聊天、补充材料、报告生成各走各的接口，没有 run_id、turn_id 和统一事件序列。

02

分析进度由前端推测

前端根据材料粗粒度状态拼接过程文字；后端没有真正推送“正在处理哪一页、发现了什么、为何进入复核”。

03

流式输出是事后切片

正式答案先由模型一次性完成，再切成 36 字发送。模型慢时，用户仍会经历一段无更新等待。

04

结果没有绑定消息轮次

分析卡片和报告附件固定渲染在聊天列表之后，旧结果可能被显示成最新 AI 回复。

05

补充材料仍走全量分析

前端上传补充材料后调用 full 模式，没有把新增 material_ids 交给 incremental；处理后也没有生成一条完整自然语言总结。

06

恢复与幂等不足

SSE 中断后退回普通请求，可能重复调用模型；刷新页面后，本地分析过程消息消失，无法从事件游标继续。
